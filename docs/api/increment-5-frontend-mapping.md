# Increment 5 frontend API mapping (implementation pending owner review)

The dashboard consumes existing backend contracts; Increment 5 adds no backend route or field. Every replay view says `REPLAYED DEMO TRAFFIC` and identifies local offline PCAP analysis. `frontend/src/visualizationApi.ts` validates the new client-facing responses; the existing `status.ts` retains upload and v1 telemetry validation. The browser presents backend decisions and crypto verification status without reimplementing those policies.

| View/action | Request | Data rendered |
| --- | --- | --- |
| Upload, protocols, flow scores | `POST /api/v1/demo/upload/analyze` (`demo.upload-analysis.v1`) | `analysis_id`, `flows[]` counted once by protocol, aligned `results[]` with original `anomaly_score`, risk, flag and explanation, `model.model_threshold`, host profiles. Upload alone does not admit a baseline. |
| Legacy first admission | `POST /api/v1/demo/baselines/evaluate` (`phase6.baseline.v1`) | One `analysis_id`; response `observation_id`, UTC capture bounds, `baseline_store_epoch`, host `current_features`, `baseline_before/after`, `decision`, reasons, readiness, confidence, probation, versions, deviations and host findings. |
| Hybrid first admission | `POST /api/v1/demo/hybrid/evaluate` (`phase7.hybrid.v1`) | Same baseline host values plus original indexed `flow_results`, `rule_assessments`, source-separated `findings`, and v2 `telemetry.eligible_count`. The dashboard never overwrites the original ML score with rule evidence strength. |
| Host history | `GET /api/v1/demo/baselines/history?host_ip=...` (`phase6.baseline.history.v1`) | Up to 32 decisions in server evaluation order, last eight accepted snapshots, epoch, current/anchor versions. Current-session observed values join by epoch + host + observation ID. Older observed values are gaps; accepted snapshot baseline values are separately labelled. |
| Flow alerts v1 | Existing `/api/v1/demo/telemetry/protect`, `/{id}/verify`, `/{id}/verify-tampered` | Manual Protect/Verify/tamper status and counts. No v1 GET status exists; status is unavailable after reload. Original v1 bytes and signed-alert schema are unchanged. |
| High unified findings v2 | `/api/v1/demo/hybrid/telemetry/protect`, `/{id}/status`, `/{id}/verify`, `/{id}/verify-tampered` | Opt-in manual Protect/Verify/tamper status and counts after eligible Hybrid evaluation only. Protected and Verified remain separate. |

The response validator rejects wrong versions, IDs, missing or nonfinite plotted values, duplicate/out-of-range flow indices and duplicate finding IDs. A 404 is shown as expired/unavailable; a 409 is shown as a conflict without retrying via the other route; 503/network errors are shown as backend unavailable; invalid schemas do not render success. The UI labels its own request **“Evaluation requested: Legacy/Hybrid”**; this is not an authoritative admission-origin field across clients or browser sessions. The backend owns one final admission per analysis.

Rule assessment `Unknown` is displayed as **Unknown / Insufficient Evidence**. `rule_evidence_strength` is a deterministic strength score, never a calibrated probability. `possible_category`, subject host(s), flow references and quantitative evidence are shown without attacker attribution. The SVG charts have equivalent semantic tables and use no synthetic client-side points or chart library.

Browser state and the backend store are both ephemeral. A new upload clears current telemetry state while retaining same-epoch observed history for the session. An epoch mismatch clears old plotted values. A backend restart loses in-memory candidates and baseline/hybrid state; saved v2 JSON cannot be verified offline after restart through these APIs. Windows host-key isolation remains **OPEN / NOT VERIFIED**.
